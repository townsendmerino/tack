## The void night

- **Run:** tack `001b5ca` ran 23:53:30–23:57:51 PDT on 2026-10-17 (night queue job `tack-e1-a1-001b5ca`, exit 0),
  tasks 1–11 without task 8. Output is in `~/tack-runs/e1/a1-2026-10-18/` on the Mac.
- **Verdict: void, because of the harness.** The sandbox denied the workspace, so the run measured neither tack nor
  the model. It is kept and never pooled with any other run.
- **Cause:**
  - `RunTack` wrote tack's `config.toml`, token and state into `task-NN/A1/`, the directory that also holds the
    repository, `task-NN/A1/repo`.
  - `tack run --edit` gives the sandbox's section `tack` the config file's directory, and that section denies both
    reading and writing there.
  - Every command was therefore refused its own working directory:
    `tack shell: could not stat …/task-NN/A1/repo: operation not permitted`.
  - The read, edit and write tools run in tack itself, outside the sandbox, so they worked. Only bash failed, so the
    model could never build or test.
- **Why the gates missed it:**
  - `TestA1RunsAndGrades` counted the bash call but not its outcome.
  - The task-7 smoke made no bash call.
- **Fix:** tack `4ea47dd`.
  - tack's files now go in a sibling directory, `task-NN/A1-tack/`.
  - `tack run --edit` refuses a workspace that overlaps its config or state directory (`sandbox.Config.Check`).
  - A sandboxed `go version` preflight voids a task whose sandbox cannot run go.
  - The test now asserts that bash succeeded, and was broken once to show that it can fail.

### First full run: stopped, void

- **Run:** 07:01:49 PDT, tack `4ea47dd`. Output is in `~/tack-runs/e1/a1-2026-10-18-day/` and its `.log`.
- **Stopped at 07:05** after six tasks, on the owner's word. **Void, because of the harness**: the sandbox could not
  build a repository whose modules were not all in the Mac's module cache.
  - In task 2 (ken), both of the model's bash calls failed: `open …/go/pkg/mod/cache/download/modernc.org/sqlite/@v/
    v1.54.0.lock: operation not permitted`.
  - The sandbox has no network and may not write the owner's module cache. opencode's runs, on nobara with no
    sandbox, could download modules.
  - Which tasks were affected depended on order, because each task's oracle runs outside the sandbox and fills the
    cache for the tasks after it.
- **Fix (tack `1819139`):**
  - Before each task, outside the sandbox and before the clock starts, `go mod download` fills the cache. Its output is
    in `modules.log`, and a failure voids the task.
  - The preflight is now `go list -deps -test ./... >/dev/null && go version` under the sandbox, so a module the
    repository needs and the cache lacks voids the task.
  - The sandbox's commands run with `GOPROXY=off`.
  - Test: `TestA1DownloadsModulesBeforeTheSandbox` uses a local module proxy and an empty cache. It was broken once:
    with the download off, the task is void and tack's message names the denied cache write.
- **Go toolchain:** the model and the oracle both use the Mac's go1.27.0, the version the task repositories ask for.
  Only tack's own `go.mod` switches up to 1.27.2. So there is no version skew between the model and the oracle.
